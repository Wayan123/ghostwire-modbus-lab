# Judge quick start

1. From the project root, run `dotnet run --project csharp/GhostWire/GhostWire.csproj` with the .NET 8 SDK. Alternatively, unzip the Windows release package, which requires the .NET 8 ASP.NET Core Runtime (x64), and run `GhostWire.exe`.
2. Open http://127.0.0.1:8000. No login, physical PLC, sensor or AI key is required for the core simulation. The case picker groups **Troubleshooting** and **Security incidents** and shows each case's difficulty. On a first visit a **Guided tour** banner suggests starting with The Silent Sensor, then Phantom Writer; its button selects The Silent Sensor, and **Dismiss** hides it for this browser. If a read setting is out of range (for example Unit ID 999), nothing is sent and a message names the allowed range.
3. Select **The Giant Pressure** and run the read. Inspect raw 39 and the simulated documentation. Set the scale to 0.01 and retest: the displayed result is 0.39 bar.
4. Open **Wire evidence (simulated frames)** under the verification line. The request is `00 01 00 00 00 06 07 03 00 0A 00 01` and the response is `00 01 00 00 00 05 07 03 02 00 27`. Tab to a field row, or hover it, to highlight its bytes; the row also states the byte range in text (for example "bytes 0–1" for the transaction ID). The panel defines MBAP header, PDU, unit ID and function code. Wire evidence is available after every read in every case, including Phantom Writer's initial read.
5. Select **The Silent Sensor**, run the initial read, inspect the timeout and possible causes. Wire evidence shows only the request frame (`00 01 00 00 00 06 01 04 00 00 00 01`) because no response arrived. Check the simulated documentation, set Unit ID to 17 and retest: the simulator returns raw 73 and the read is verified. The timeout alone did not prove the unit ID was the cause; the successful retest with 17 is what verifies the setting.
6. Select **The Wrong Register**, run the read and open Wire evidence: the response `00 01 00 00 00 03 03 84 02` decodes as function `84 · Exception for 04` and exception code `02 · Illegal Data Address`. Compare address 21 to the simulated zero-based map at 20, then retest with 20: the simulator returns raw 125 and the read is verified.
7. Select **Phantom Writer** (security, intermediate) and run the initial read (unit 5, function 03, address 100, quantity 1, scale 0.1). The simulator returns raw 950, shown as 95 °C, while the simulated documentation states a normal setpoint of 650 (65.0 °C). The read verifies the current simulated setpoint, not who changed it.
8. In **Simulated traffic log**, review the 12 captured transactions. Identify the entry that changed the setpoint: its simulated time, client label, transaction ID, unit ID, register and old and new value. Times show as HH:MM:SS (UTC); hover a time, or use a screen reader, for the full timestamp. Press **Show frames** on a row to see its bytes. On a narrow screen the table scrolls sideways inside its own box. Type the transaction ID and client label of that entry into the answer form, then press **Submit answer**. After 3 answers that are not verified, a training hint appears under the form, and a second one after the 4th. The hints never name the entry.
9. Expected verified outcome: transaction 1111 at 2026-10-31T02:13:33Z from client label MAINT-LAPTOP-07 is function 06 (Write Single Register) to unit 5, register 100, value 950; the last read before it (transaction 7) returned 650 and the next read (transaction 8) returned 950. The row is then marked "⚠ Unauthorized write", and four mitigations appear under "Next steps · real-world guidance, not verified by this simulation". A wrong pair returns "not verified" without revealing the correct one.
10. Select **The Night Scanner** (security, intermediate) and run the initial read (unit 5, function 03, address 100, quantity 1, scale 0.1). The simulator returns raw 650, shown as 65 °C, which matches the documented normal value, and the read is verified. A normal read does not show which other clients queried the gateway.
11. In **Simulated traffic log**, review the 15 captured transactions. The **Status** column shows each result as text: "Response", "Timeout (no reply)" or "Exception 02 · Illegal Data Address". `HMI-01` polls unit 5 every 5 s (transactions 1–5, all 650). Find the client that asks many different unit IDs, and type the transaction ID of its **first** request and its client label into the answer form. After 3 answers that are not verified, training hint 1 appears ("Look at the Unit ID column: does any client ask many different units?"), and after the 4th, hint 2 ("Find the first request in that run.").
12. Expected verified outcome: client label ENG-WS-13 sent 10 FC03 reads of address 0 to unit IDs 1 to 10 in increasing order, transactions 301 (2026-11-01T03:12:07Z) to 310 (03:12:16Z), 1 s apart. Eight timed out, unit 5 returned exception 02 (it has no register 0), and unit 9, which the simulated documentation does not list, answered with raw 1. The row for transaction 301 is marked "⚠ First scan request", and four mitigations appear: asset inventory and a polling baseline, IDS rules for unit-ID sweeps, restricting which hosts can reach port 502, and logging at the gateway. Reading unit 9 or unit 1 through the read form gives the same response or timeout as the log.
13. Inspect observations, hypotheses, training hints, verification and case history (reads and answer attempts). The report can be printed via the browser.

All devices and measurements are simulated. The server is limited to loopback; it cannot test or write real equipment. Learners cannot send Modbus writes; the Phantom Writer FC06 happens only inside the server's private simulator at startup. The Night Scanner sweep is 10 FC03 reads against a private loopback gateway simulator at startup, not a network scan. Modbus TCP frames carry no client identity, so client labels are capture metadata. Mitigations are guidance and are not verified by this simulation. Timeout is not proof of a particular cause.
