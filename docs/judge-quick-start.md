# Judge quick start

1. From the project root, run `dotnet run --project csharp/GhostWire/GhostWire.csproj` with the .NET 8 SDK.
2. Open http://127.0.0.1:8000. No login, physical PLC, sensor or AI key is required for the core simulation. The case picker groups **Troubleshooting** and **Security incidents** and shows each case's difficulty.
3. Select **The Giant Pressure** and run the read. Inspect raw 39 and the simulated documentation. Set the scale to 0.01 and retest: the displayed result is 0.39 bar.
4. Open **Wire evidence (simulated frames)** under the verification line. The request is `00 01 00 00 00 06 07 03 00 0A 00 01` and the response is `00 01 00 00 00 05 07 03 02 00 27`. Tab to a field row, or hover it, to highlight its bytes; the row also states the byte range in text (for example "bytes 0–1" for the transaction ID). The panel defines MBAP header, PDU, unit ID and function code.
5. Select **The Silent Sensor**, run the initial read, inspect the timeout and possible causes. Wire evidence shows only the request frame (`00 01 00 00 00 06 01 04 00 00 00 01`) because no response arrived. Check the simulated documentation, set Unit ID to 17 and retest.
6. Select **The Wrong Register**, run the read and open Wire evidence: the response `00 01 00 00 00 03 03 84 02` decodes as function `84 · Exception for 04` and exception code `02 · Illegal Data Address`. Compare address 21 to the simulated zero-based map at 20, then retest with 20.
7. Select **Phantom Writer** (security, intermediate) and run the initial read (unit 5, function 03, address 100, quantity 1, scale 0.1). The simulator returns raw 950, shown as 95 °C, while the simulated documentation states a normal setpoint of 650 (65.0 °C). The read verifies the current simulated setpoint, not who changed it.
8. In **Simulated traffic log**, review the 12 captured transactions. Identify the entry that changed the setpoint: its simulated time, client label, transaction ID, unit ID, register and old and new value. Expand **Frames** on a row to see its bytes. Press **Select** on the row to copy its transaction ID and client label into the answer form, then **Submit answer**.
9. Expected verified outcome: transaction 1111 at 2026-10-31T02:13:33Z from client label MAINT-LAPTOP-07 is function 06 (Write Single Register) to unit 5, register 100, value 950; the last read before it (transaction 7) returned 650 and the next read (transaction 8) returned 950. The row is then marked "⚠ Unauthorized write", and four mitigations appear under "Next steps · real-world guidance, not verified by this simulation". A wrong pair returns "not verified" without revealing the correct one.
10. Inspect observations, hypotheses, training hints, verification and case history (reads and answer attempts). The report can be printed via the browser.

All devices and measurements are simulated. The server is limited to loopback; it cannot test or write real equipment. Learners cannot send Modbus writes; the Phantom Writer FC06 happens only inside the server's private simulator at startup. Modbus TCP frames carry no client identity, so client labels are capture metadata. Mitigations are guidance and are not verified by this simulation. Timeout is not proof of a particular cause. External AI is optional and may be wrong.
